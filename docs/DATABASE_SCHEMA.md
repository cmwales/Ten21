# Database Schema

A concrete, table-by-table reference for the actual PostgreSQL schema, generated by reading
the current EF Core entities/configurations/migrations directly (not aspirational — if this
disagrees with the code, the code wins; open a PR against this file, not the other way
around). `DATA_MODEL.md` describes the domain model at a conceptual level; this doc is the
"what tables actually exist, what's in them, which ones have RLS" reference for anyone
connecting a SQL client directly (see the root `README.md` for connection details).

Source of truth for anything more precise than what's summarized here: the entity classes in
`src/Ten21.Domain/Entities/`, their Fluent configurations in
`src/Ten21.Infrastructure/Persistence/Configurations/`, and the migration history in
`src/Ten21.Infrastructure/Migrations/`.

## Conventions used throughout

- **Multi-tenancy**: every `ITenantScopedEntity` carries a `TenantId` column, enforced by an
  EF Core global query filter (`Ten21DbContext.OnModelCreating`) AND, for most such tables, a
  Postgres Row-Level Security policy keyed on `current_setting('app.current_tenant_id')` --
  see the "Row-Level Security coverage" section below for exactly which tables have RLS and
  which are deliberately excluded.
- **Soft delete**: `IAuditableEntity`/`ISoftDelete` entities carry `CreatedAt` and
  `IsDeleted`; a global query filter hides `IsDeleted = true` rows automatically. Tables
  without `IsDeleted` in the column list below don't implement `ISoftDelete` -- removing a
  row is a genuine delete for those (see each entity's own class comment for why).
- **Who/when columns**: every `IAuditableEntity` table also carries `CreatedByUserId`
  (nullable -- null for background/seed operations with no resolved user context),
  `UpdatedAt`, and `UpdatedByUserId` (both null until the row's first update after creation).
  All three are stamped automatically by `AuditSaveChangesInterceptor` -- nothing sets them
  manually. `CreatedAt` itself is set explicitly by whichever controller creates the row, not
  by the interceptor (see `IAuditableEntity`'s own comment for why it's the one exception).
  A soft-delete counts as an update for this purpose (`UpdatedAt`/`UpdatedByUserId` get
  stamped on it too) -- it IS one, at the database level.
- **Audit trail**: every `IAuditableEntity` change (insert/update/soft-delete) is *also*
  captured as a full JSON diff into `audit_logs` by the same interceptor, in the same
  transaction -- the who/when columns above are a fast "last touched" summary on the row
  itself; `audit_logs` is the complete history (every change, not just the latest).
- **Naming**: C# entity `PascalCase` maps to `snake_case` table names (explicit `ToTable(...)`
  calls, not EF's default pluralization) and to the .NET-standard column casing preserved
  as-is (e.g. `"TenantId"`, not `tenant_id` -- see `InitialCreate`'s own migration comment for
  why RLS policies quote column names exactly).

## Tenancy & Identity

| Table | Purpose | Key columns / relationships |
| --- | --- | --- |
| `tenants` | One row per isolated HOA / property corporation / self-storage facility -- every `TenantId` FK across the schema points here. NOT itself tenant-scoped (a tenant can't belong to itself). | `Id`, `Name`, `OrganizationId` (nullable, parent PMC), `PortfolioSize`, `CreatedAt` |
| `organizations` | Parent PMC container for multiple `tenants`. NOT tenant-scoped -- sits above the tenant boundary. Self-managed HOAs never get a row here. | `Id`, `Name`, `SubscriptionTier`, `CreatedAt` |
| `tenant_memberships` | Bridges a global `users` identity to a role scoped to one tenant -- "which properties can this person act in, and as what role." One person can have several rows (multi-property PMC staff, an owner who's also a board member elsewhere). **Deliberately excluded from RLS** -- see its own note below. | `Id`, `TenantId`, `UserId`, `RoleId`, `IsPrimary` (exactly one per user, enforced in app logic not a DB constraint), `CreatedAt` |
| `users` | ASP.NET Core Identity's `ApplicationUser` -- one row per person, global, no `TenantId` at all (tenant/role scoping lives entirely in `tenant_memberships`). | `Id`, `Email`/`NormalizedEmail`/`PasswordHash` (Identity plumbing), `FirstName`, `LastName`, `IsActive`, `Address`, `AgreedToTermsAt`, `MustChangePassword`, `CreatedAt` |
| `roles` | ASP.NET Core Identity's `ApplicationRole` backing the 9-tier `RoleNames` taxonomy (SuperAdmin, PropertyManager, BoardMember, PropertyOwner, Tenant, Vendor, CommitteeMember, OnSiteStaff, Accountant). Thin subclass, no extra columns yet. | `Id`, `Name`, `NormalizedName` |
| `user_roles`, `user_claims`, `user_logins`, `user_tokens`, `role_claims` | Standard ASP.NET Core Identity junction/claims tables (`IdentityUserRole<Guid>` etc.), just renamed to snake_case. | Identity-framework standard shape |
| `refresh_tokens` | Rotating 7-day refresh tokens (HTTP-only cookie delivery). Carries `TenantId` as a plain column but is **NOT** `ITenantScopedEntity` -- the refresh endpoint runs before any tenant context is resolved, so the global query filter would zero out every lookup. | `Id`, `UserId`, `TenantId`, `TokenHash` (SHA-256, raw value never persisted), `ExpiresAt`, `CreatedAt`/`CreatedByIp`, `RevokedAt`/`RevokedByIp`, `ReplacedByTokenId` (rotation chain) |

## Property & Setup

| Table | Purpose | Key columns / relationships |
| --- | --- | --- |
| `properties` | A single leasable space -- a whole house, OR one suite within a building. **Flat by design**: there is no parent/child Property-and-Unit split (reversed from an earlier design after tester feedback -- see `User_Stories_Sprint_3.md`'s "Flatten Property/Unit" addendum). Two suites in the same building are two independent rows sharing a street address, distinguished by `UnitIdentifier`. | `Id`, `TenantId`, `Name`, `PropertyType`, address fields (`StreetAddress1/2`, `City`, `State`, `PostalCode`, `Country`), `UnitIdentifier`, `TargetRent`, `OccupancyStatus`, `UnitGroupId`/`UnitTierId` (optional matrix-editor tags), `MoveOutNoticeDate`, `AllowTenantDirectory`, `CreatedAt`, `IsDeleted` |
| `unit_groups` | Reusable, workspace-scoped physical section/phase label (e.g. "North Wing") assignable to any `properties` row. Independent of `unit_tiers` -- not a hierarchy. | `Id`, `TenantId`, `GroupName`, `Description`, `CreatedAt`, `IsDeleted` |
| `unit_tiers` | Reusable, workspace-scoped pricing label (e.g. "Ocean View 2BR"). Assigning one seeds `properties.TargetRent` at assignment time only -- not a live-recalculated relationship. | `Id`, `TenantId`, `TierName`, `DefaultRent`, `AccountingCode`, `Description`, `CreatedAt`, `IsDeleted` |

## Residents & Leasing

| Table | Purpose | Key columns / relationships |
| --- | --- | --- |
| `resident_profiles` | One occupant (primary or secondary) of a specific `properties` row. Its own entity, not a repurposed `tenant_memberships` row -- occupancy history (move-in/move-out) is a different, soft-deletable concern from "this login has this role." `UserId` links to a provisioned login once/if one exists. | `Id`, `TenantId`, `PropertyId` (`DeleteBehavior.Restrict` -- can't delete a property with residents), `UserId` (nullable), `OccupantType`, `FirstName`, `LastName`, `Email`, `PhoneNumber`, `ForwardingAddress`, `NoticeGivenDate`, `ShowInDirectory`, `CreatedAt`, `IsDeleted` |
| `emergency_contacts` | One-to-many off `resident_profiles` (`DeleteBehavior.Cascade`). Not soft-deletable -- removing one is a genuine delete. | `Id`, `TenantId`, `ResidentProfileId`, `Name`, `PhoneNumber`, `Relationship`, `CreatedAt` |
| `leases` | Binds one `resident_profiles` row to one `properties` row with contract dates, base rent, and a billing anchor day. `TotalMonthlyDues` is deliberately NOT stored -- computed at read time from `MonthlyBaseRent` + `SUM(lease_recurring_charges.Amount)`. | `Id`, `TenantId`, `PropertyId`, `ResidentId`, `StartDate`, `EndDate`, `MonthlyBaseRent`, `DueDayOfMonth` (1-28), `Status`, `CreatedAt`, `IsDeleted` |
| `lease_recurring_charges` | One recurring monthly sub-charge on a lease (e.g. "Pet Rent"). Not soft-deletable -- removing a line item is a genuine delete. | `Id`, `TenantId`, `LeaseId`, `ChargeName`, `Amount`, `AccountingCode`, `CreatedAt` |

## Charges & Ledger

| Table | Purpose | Key columns / relationships |
| --- | --- | --- |
| `charges` | Any billable line item posted to a unit's ledger -- one-time fines, pro-rated move-in charges, or a period's rent/add-ons, all the same shape (renamed from `ManualCharge` once it grew to cover rent too). Always billed to the **unit** (`PropertyId`), never to an individual resident. `PaymentStatus` is NOT stored -- computed at read time from allocations vs `Amount`. | `Id`, `TenantId`, `PropertyId`, `Description`, `Amount`, `DueDate`, `AccountingCode`, `Notes`, `Category`, `AllocationPriority` (1=highest, statutory-default per category), `IsStatutoryLocked`, `Status` (Active/Voided), `CreatedAt`, `IsDeleted` |
| `charge_adjustments` | A credit/debit correction against a charge that already has payments applied (so its `Amount` is locked). Mandatory `Reason` (5-250 chars) for audit compliance. Append-only -- no soft delete, no edit/delete action. | `Id`, `TenantId`, `TargetChargeId`, `AdjustmentType`, `Amount`, `Reason`, `CreatedAt` |

## Payments, Credits & Deposits

| Table | Purpose | Key columns / relationships |
| --- | --- | --- |
| `payment_transactions` | One row per payment received (cash/check/Zelle/etc. -- live tokenized processing is Phase 2). `UnallocatedAmount` is the mutable running overpayment-credit balance produced by this payment, drawn down over time by `credit_allocations`/`refund_transactions`. `Status`/`ReversalReason`/`ReallocatedToId` support reversing an NSF/misposted payment without deleting the row. Append-only otherwise. | `Id`, `TenantId`, `PropertyId`, `ResidentProfileId`, `PaymentDate`, `AmountPaid`, `TenderType`, `ReferenceNumber`, `Notes`, `UnallocatedAmount`, `Status`, `ReversalReason`, `ReallocatedToId`, `CreatedAt` |
| `payment_allocations` | The actual application of (a portion of) one payment to one charge -- a genuine many-to-many join (one payment can span several charges via the statutory waterfall; one charge can receive partial payments from several transactions over time). | `Id`, `TenantId`, `PaymentTransactionId`, `ChargeId`, `AllocatedAmount`, `CreatedAt` |
| `credit_allocations` | Draw-down of a payment's previously-unallocated credit against a charge that didn't exist yet (or wasn't outstanding) when the payment was logged -- a later, separate event from `payment_allocations`, triggered by a PM manually running "Apply Credits to Charges" (deliberately not a scheduled job). | `Id`, `TenantId`, `SourcePaymentTransactionId`, `TargetChargeId`, `AppliedAmount`, `AppliedDate`, `CreatedAt` |
| `refund_transactions` | An outbound disbursement to a resident -- either unapplied overpayment credit, or leftover security deposit after move-out settlement. Doesn't link back to which payment(s) supplied the credit (draw-down is oldest-payment-first at refund time). Append-only. | `Id`, `TenantId`, `ResidentProfileId`, `PropertyId`, `Amount`, `RefundDate`, `TenderType`, `ReferenceNumber`, `Reason`, `CreatedAt` |
| `security_deposits` | A deposit collected at move-in, held as a **liability** separate from rental income until move-out -- deliberately NOT a `Charge`, so it can never look like rent being paid. `AmountHeld` starts at `OriginalAmount` and is drawn down once, atomically, at settlement. | `Id`, `TenantId`, `PropertyId`, `ResidentProfileId`, `OriginalAmount`, `AmountHeld`, `CollectedDate`, `Status`, `CreatedAt` |
| `deposit_settlement_allocations` | The deposit-money equivalent of `payment_allocations`/`credit_allocations`, kept as its own table so a settled deposit is never counted as rental income in ledger math (`UnitStatementResponse.Balance` tracks it as its own term). | `Id`, `TenantId`, `SecurityDepositId`, `TargetChargeId`, `AppliedAmount`, `AppliedDate`, `CreatedAt` |

| Table | Purpose | Key columns / relationships |
| --- | --- | --- |

## The Community Directory has no table of its own

Worth calling out because it's easy to go looking for one: the community directory (dual
opt-in resident-facing neighbor list, plus the PM-facing verification view) is **computed
live**, not stored. It's the join of `properties.AllowTenantDirectory = true` +
`resident_profiles.ShowInDirectory = true` for properties sharing a street address, gated by
`workspace_settings.EnableCommunityDirectory`. See `DirectoryController` for both the
Tenant-facing (`GET /api/directory`) and PM-facing (`GET /api/directory/admin`) queries.

## Row-Level Security coverage

Two-layer tenant isolation is a non-negotiable rule (see `CLAUDE.md`) -- the EF Core global
query filter is layer one; a Postgres RLS policy (`sql/rls-policies.sql`, applied via
migrations) keyed on `current_setting('app.current_tenant_id')` is layer two. As of the RLS
backfill (2026-08-27), **18 tables have RLS enabled and forced** (`FORCE ROW LEVEL SECURITY`,
so it applies even to the table-owner role):

`properties`, `document_attachments`, `audit_logs` (original, from `InitialCreate`), plus
`charges`, `charge_adjustments`, `payment_transactions`, `payment_allocations`,
`credit_allocations`, `refund_transactions`, `security_deposits`,
`deposit_settlement_allocations`, `leases`, `lease_recurring_charges`, `unit_tiers`,
`unit_groups`, `resident_profiles`, `emergency_contacts`, `workspace_settings` (backfilled).

**Deliberately excluded from RLS**, each for a specific reason, not an oversight:

- `tenant_memberships` -- login/context-switch queries run *before* a tenant context is
  resolved (the same bootstrap problem `refresh_tokens` has); an RLS policy here would zero
  out every login attempt. Protected by the EF Core global query filter alone.
- `refresh_tokens` -- not `ITenantScopedEntity` at all (see its own table note above);
  looked up by opaque token hash, not a tenant-scoped listing operation.
- `tenants`, `organizations` -- sit above the tenant boundary by design; not tenant-scoped,
  nothing to isolate a tenant *from*.
- `users`, `roles`, `user_roles`, `user_claims`, `user_logins`, `user_tokens`, `role_claims`
  -- ASP.NET Core Identity's own tables; identity is global, tenant/role scoping lives in
  `tenant_memberships` instead.

The running Postgres role the app connects as (`ten21_app`) must be neither a superuser nor
the owner of these tables, or Postgres silently exempts it from every RLS policy regardless
of `FORCE` -- see `sql/rls-policies.sql`'s own note.

## Enum reference

Enums live in `src/Ten21.Domain/Enums/` -- consult that folder directly for exact member
lists; noted here only for which table each governs: `PropertyType`/`OccupancyStatus`
(`properties`), `OccupantType` (`resident_profiles`), `LeaseStatus` (`leases`),
`ChargeCategory`/`ChargeLifecycleStatus`/`ChargePaymentStatus` (`charges`, the last one
computed not stored), `AdjustmentType` (`charge_adjustments`), `TenderType`/
`PaymentTransactionStatus` (`payment_transactions`), `RefundReason`/`RefundTenderType`
(`refund_transactions`), `SecurityDepositStatus`/`AccountStatus` (`security_deposits` and
computed unit-statement status respectively), `MatrixBatchField`/`StatementDateRange`
(request-shaping enums, not persisted columns).
